# 不烧心 · 给观众讲的方案

> 面向"从没听过这个插件"的观众。目标不是让他们记住功能列表，
> 而是让他们**在下次看到 `--force` 时想起隔壁那家黑心店**。
>
> 全程 8–10 分钟。三个可以现场做的动作，其余全在讲。

---

## 一、先定一句话（全场只说这一句核心）

> **它不改代码，不改模型，不提效率。它改的只是你听警告时的注意力。**

这句话要在开场 30 秒内说完，之后每次有人问"这有什么用"，都回到这句。

**不要用的表述**（用了当场失去信任）：

| ❌ 别说 | ✅ 改说 |
|---|---|
| 提升开发效率 | 让警告更容易被记住 |
| 智能优化对话 | 给技术取舍换一个归因框架 |
| 代码质量保障 | 不改一行代码 |
| 各种场景全覆盖 | 中文语境、技术话题、玩梗场景 |

---

## 二、开场：先讲观众的痛（90 秒）

**逐字稿：**

> 我先问一个问题：你们上一次看到有人用 `--force` 装依赖，是在什么时候？
>
> （停顿，等人点头）
>
> 我猜大部分人都见过。而且我猜，当时**一定有人说了"别这么干"**——可能是你，可能是旁边的人，可能是一条 review 评论。
>
> 那句话是正确的。它也是**没用的**。
>
> 为什么？不是因为它错。是因为它和我们每天看的几百条技术提示**长得一模一样**：一句正确的、冷漠的、没有代价感的陈述。
>
> 助手说「不建议使用 `--force`，会导致 lockfile 不一致」——你说"哦"，然后用了 `--force`。
>
> 这个插件赌的是另一件事：**如果你把这条警告换成一个有角色、有代价、有翻车的故事，你下次会想起来。**
>
> 它做的事就这一件。不改代码，不改模型，不提效率。

---

## 三、同一件事，两种说法（现场演示 1，2 分钟）

**先说标准版**（口头念，不要投屏代码）：

> 不建议使用 `--force`，它会导致 lockfile 与 package.json 不一致，可能引发构建失败。

**然后现场敲：**

```
/bushaoxin_rewrite preset=特辣 npm install --force 之后本地能跑，CI 挂了
```

**投屏结果，逐句念出来**（真实引擎输出）：

> 那家「一键装依赖」的店挂出招牌：**「充值即送 `--force`，三秒解决，包过。」**
>
> 你去了。三秒钟，`node_modules` 炒得喷香，`package-lock.json` 也顺手给你改了。
>
> 三分钟后构建在 CI 上翻车。那锅料端出来的时候谁都看懂了——**它压根没看你的 Node 版本。**

**话术（关键在这一句）：**

> 注意最后那行：**技术真话：`--force` 会让 lockfile 与 `package.json` 脱节。**
>
> 技术信息一个字没少。少的是"你听完就忘"这件事。
>
> 下次你在终端里准备敲 `--force`，脑子里响的不会是"不建议使用"，而是"隔壁那家黑心店"。

---

## 四、它靠什么生效（1 分钟，建立技术可信度）

**这一段决定观众信不信你，不要跳。**

> 说个技术事实，证明我不是在事后加工。
>
> 我一开始想做的是"事后改写助手的回复"。**做不到。**
>
> 我扒了宿主的源码：`assistant/message` 这个事件是在消息**写进会话之后**才发出来的；而客户端是跟着 `agent/assistant-stream` 的**流式帧**实时渲染的。等你拿到全文，用户早看见了。**没有钩子能改。**
>
> 所以我们走的是唯一有效的路：**在生成之前，把文风写进系统提示。** 助手的回复从一开始就是那个风格，不是贴上去的。
>
> 这就是为什么插件里有个"文风层"——它是靠 `systemPrompt.section` 注入的，不是补丁。

---

## 五、它不止会复读一句台词（现场演示 2，2 分钟）

> 有人会问：这不就是把"贵是贵了点，但吃了不烧心"到处贴吗？
>
> 恰恰相反。那个梗之所以后来被人嫌，就是因为**AI 批量复读它**。这个插件的第一条禁令就是：不许照抄原台词。

**现场连敲三条，换话题：**

```
/bushaoxin_rewrite preset=干辣 catch {} 是空的，建议处理异常
/bushaoxin_rewrite preset=中辣 报告日期比实际早一天
/bushaoxin_rewrite preset=特辣 本地 .env 能跑，数据不对查了一下午
```

**指给观众看这三处的不同：**

| 话题 | 它换的说辞 |
|---|---|
| 依赖 | 「锁要对得上版，版要对得上货」 |
| 异常 | 「账要记」 |
| 时区 | 「钟要对得上灶」 |
| 密钥 | 「钥匙不进仓库」 |

**话术：**

> 骨架是同一个（便宜的路有坑、慢的路可靠），但**每一行的行话都不一样**。
>
> 而且看这条——「干辣」档：**招牌台词出现 0 次**。但你还是认得出是这个梗，因为它靠的是骨架，不是复读。

---

## 六、它不演小剧场（1 分钟，这是最重要的边界）

> 我特意加了一条禁令，这条对你们可能最有价值：
>
> **文风层只改说话方式，不许写角色对白、不许加旁白、不许加【镜头】。**
>
> 为什么？因为我试过不管它——助手会开始角色扮演，然后一次技术讨论就变成了一场小剧场。那是灾难。
>
> 要剧本？显式调 `bushaoxin_drama`。日常对话里，它只是换了个说法，没有在演。

---

## 七、两条底线（30 秒，收尾立信任）

> 最后两条，是代码层面写死的，不是我在文档里承诺的：
>
> 第一，**每篇改写末尾永远附一行真实技术结论**，不可关闭。段子可以让路，事实不行。
>
> 第二，**不许为了配合段子编造技术事实**。这条写在注入给模型的文风指令里。
>
> 所以它是一层糖衣，不是一层谎。**糖衣会化，药还在。**

---

## 八、怎么自己试（30 秒）

> 装完之后：
>
> - 输入框上方会多一行「🔥 不烧心」。**点一下，向上拉出一条滑条**，四个档位：关 / 轻 / 中 / 重。
> - 拖到你想要的辣度，松手即生效。这个档位**只影响你这一段会话**，别人不受影响。
> - 拖错了再拖回去，不用重启。
>
> 想验它真的写进去了（不是假控件）：浏览器打开
> `http://127.0.0.1:19387/dsh-bushaoxin/style?session=<你的会话号>`
> 返回的 `level` 和滑条位置一致，就是写通了。写不进去时，面板会**直接告诉你没写进去**。

## 九、问答预案

**Q：这不就是个玩具？**
> 是个玩具。但它是个**有原则的玩具**：每篇必带真实结论、禁止编造事实、禁止在事故排查时用。
> 玩具的边界写清楚了，它就不会变成事故。

**Q：英文用户能用吗？**
> 不能。"不烧心"是中文网络梗，翻译过去就死了。这是它的边界，不是缺陷——我宁愿它窄而准。

**Q：会不会干扰正经工作？**
> 三个安全阀：① 文风强度可以调到「关」；② 排查线上事故时不启用；③ 它不改工具参数、不拦执行、不写你的配置。

**Q：为什么不做成"提高效率"的工具？**
> 因为它确实不提高效率。往那上面写就是骗人，而且一眼假——用户装上发现啥也没多，信任就没了。

**Q：现在有什么已知缺陷？**
> 有一个，我主动说：系统提示里那段文风正文是**插件加载时定死的**，滑条改了宿主状态、也改了本轮回复，但那段正文在本次运行内不会跟着变。彻底修需要让强度走一个每轮可变的通道。**这个我还没做。**

## 十、讲之前先跑一遍（防止翻车）

```bash
npm run demo     # 重建台本产物（201 行，可直接投屏）
npm test         # 32/32 + 一期全过
```

**演示前必做：刷新页面**（客户端 bundle 是插件现读磁盘的，刷新即最新）。

**别在演示时现场输入的文本**：任何没有具体技术线索的泛泛描述（比如"CI 红了怎么办"）。
那种输入会让引擎落到"通用"剧本，输出会泛。**演示用卡里那几条都命中具体线索，安全。**
